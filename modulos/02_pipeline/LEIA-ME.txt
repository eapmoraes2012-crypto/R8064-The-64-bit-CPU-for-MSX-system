MODULE 02 - 7-stage pipeline (trace-driven timing model) - 2026-11-02
Files: rtl/r8064_pipe.v, rtl/tb_pipe.v, ref/gen_trace.py (generates traces and table), ref/run_pipe.py (runs Icarus and compares), resultado_pipeline.txt, sim/*.mem (11 programs).
How to run: copy rom/*.mem and rtl/r8064_decode.v from the package + rtl/*.v + sim/*.mem to a folder; python3 ref/gen_trace.py <package> <folder>; python3 ref/run_pipe.py <folder>.

WHAT IT IS: an F1,F2,D,R,X,M,W pipeline in RTL that executes the instruction TRACE (b2,b3) and counts clocks: single bus (fetch x data, data has priority),
wait per access (1+W), taken branch with wrong-path fetch until resolved in D/X/M (penalty 2/4/5 comes from the structure itself), and the REAL decoder
r8064_decode in the D stage (checked against the combinational read of the ROMs: 500/500 checks, 0 errors; a mutant of the control ROM was detected).
WHAT IT IS NOT: it does not execute the instructions (there is no data/registers/memory) and does not model data hazards (RAW, load-use), not-taken branches, interrupts, FPU/MMU.
Not synthesizable (uses trace and simulation ROMs); therefore there is no LUT/Fmax for this module.

RESULTS (ver resultado_pipeline.txt)
A/B  D=1, sequential fetch (spreadsheet assumption): isolated instruction, ALU sequences and long EX match the spreadsheet EXACTLY (+6 fill).
     With a mix of memory and branches the pipeline is 0% to 3% faster (A) or 0.1% to 10% (B), because the spreadsheet adds penalty and wait without overlapping.
C    D=2 (decoder as it is: id +1, control +2): +1 clock of latency and BR_D goes from 2 to 3 (JPQ: +5.5%); the rest equal or up to 16% below the spreadsheet.
D    SERIAL fetch (only fetches the next instruction after knowing the length, len in 2 clocks): 5% to 60% WORSE than the spreadsheet.
CONCLUSOES
1) The spreadsheet only holds if fetch is anticipated (prefetch queue + length decoder off the critical path). The R8064 has instructions of 2 to 13 bytes and
   the length depends on b2/b3 (ROM). Without prefetch, CPI rises from 5.06 to 8.04 in ALU code with wait. The prefetch queue still has to be designed (future module).
2) Answer to "two serial reads in D": it works if D takes 2 clocks (cost: +1 latency, BR_D=3). Alternative: read the control ROM in the R stage (D=1) and keep
   BR_D=2 only if the branch class can be obtained from ROM_A/B (today it is only in the control ROM). Not tested.
3) Branch penalties are partially hidden behind the busy bus; the spreadsheet sum is conservative.
ASSUMPTIONS: W_RD=4,W_WR=2,W_IO=1, HIT=0 (those of the spreadsheet); branches always taken ("false" conditionals not simulated); 1 fetch access of 8 bytes per instruction (no reuse).

=== PREFETCH QUEUE (rtl/r8064_pipe2.v, rtl/tb_pipe2.v, ref/run_pipe2.py, resultado_prefetch.txt) ===
Front-end: fetch of aligned 8-byte words (1+WRD clocks, contends for the bus with M) -> queue of QCAP bytes -> F1 (length, LEN_LAT clocks) -> F2 (extracts LEN bytes) -> D.
Branch: the branch instruction stalls the front-end on entering F1; the queue keeps filling with wrong-path bytes until resolution (D/X/M); then it is flushed and fetch restarts
at the target (pseudo-random offset within the word). Does not model data hazards or not-taken branches. Real decoder in D checked: 500/500, 0 errors.
How to run: python3 ref/run_pipe2.py <working folder>  (the same folder as module 02, with the ROMs; optional arguments = configuration indices).
RESULTS (CPI = clocks per instruction; spreadsheet = fetch of 1 word per instruction, no reuse)
- With the spreadsheet's wait and a 32 B queue: 10% to 61% FEWER clocks than the spreadsheet (e.g.: ALU 5.06 -> 2.13 CPI; random mix 13.99 -> 10.76). The spreadsheet OVERESTIMATES fetch,
  because one 8-byte word serves several 2-5 byte instructions. Calls/returns (CALL/RET) stay equal to the spreadsheet (+0.3%): the branch penalty dominates.
- Queue size: 18 and 19 B deadlock (13-byte instruction + 8-byte word do not fit); functional minimum = 20 B (13+8-1); 24 B has the same performance as 32 and 64 B
  (difference < 0.1% in 500 instructions; 16 B deadlocks in several programs). Recommended: 32 B (2 BSRAM not needed; fits in registers/SSRAM). 
- Branches: a wait of 4 leaves about 14 words fetched until resolution; the branch in D costs 1 more clock with D=2 (JPQ BR_D 3).
- WITHOUT wait (cache/fast memory): the length decoder with LEN_LAT=2 is NOT pipelined and limits to 1 instruction every 2 clocks (ALU: CPI 2.08 against 1.06 of the spreadsheet, +96%).
  To sustain 1 instruction/clock the length decoder needs 1 clock per instruction (or to be pipelined/duplicated). With a wait of 4 this does not show up.
ASSUMPTIONS TO CONFIRM: 8-byte fetch word (64-bit bus), W_RD=4, no cache hits, branch target with random offset, F1 reads the length in LEN_LAT clocks.
