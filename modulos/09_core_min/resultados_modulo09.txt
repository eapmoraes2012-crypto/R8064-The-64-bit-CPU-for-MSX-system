MODULE 09 - Synthesizable minimal core of the R8064 (area skeleton) - 2026-11-04
GOAL: measure how much the core (fetch, decode, pipeline, forwarding, ALU, LSU, register file, timer) occupies on the GW2AR-18, to validate the "Core = 4,800 LUT4" line of the lean budget.
WHAT IT IS: rtl/r8064_core_min.v. 32 B prefetch queue + 13-byte aligner, REAL ED decoder (r8064_decode: ROM_A/ROM_B/ctrl) and main page ROM,
  48-bit microoperation ROM (BSRAM, pseudo-random content in synthesis), 64x64 register file in BSRAM (module 01) with 3 reads, EXX/EX AF register mapping,
  immediate extraction, forwarding X2/M/W + load-use interlock comparator, 2-stage ALU (alu_prep/alu_core of module 01), address and branch-target adders,
  64-bit LSU (alignment and extension), flags, branch resolved in X2 (flushes the queue), 64-bit timer + interrupt.
WHAT IT IS NOT: it does not have the semantics of the ~1,480 instructions (only a test mini-set: LDI, 3-operand ADD, LD, ST, ADDI, JR, JRNZ), nor multi-step CALL/RET/PUSH/POP, I/O, strings (LDIR...),
  nor partial-write hazards. The front-end issues 1 instruction every 4 clocks (ROM A/B and ROM ctrl/uop in series): it does NOT sustain 1 instruction/clock.
SIMULATION (Icarus; sim/tb_core.v): 21-byte program (loop of 5 iterations: add, ST, ADDI on the pointer, ADDI -1, JRNZ, then LD): registers and 5 memory words match. RESULT: TEST PROGRAM OK.
  Bug found and fixed in the simulation: after flushing the queue (branch) the "drop" flag stalled the fetch (the withdrawn request never received an ack).
SYNTHESIS / P&R (Yosys 0.70 + nextpnr-himbaechel, GW2AR-LV18QN88C8/I7, 100 MHz, router2, LFSR wrapper of ~130 FF):
  LUT4 4,904 (23 %) [~4,800 without the wrapper], ALU (carry chains) 426, MUX2 1,065+162+53+11, FF 2,275 (14 %), BSRAM 15, Fmax 78.8 MHz (FAILS at 100).
  Critical path: 64-bit ALU (ctl_x2 -> alu_core -> flags/fl) ~12.7 ns. Fixed with one more pipeline stage in the ALU/flags (the isolated ALU of module 01 closed at 110 MHz).
  Detail per module (synthesis without flattening, counts per instance): alu_core 773 LUT, alu_prep 2,200 LUT (isolated; flattened inside the core it drops a lot), r8064_decode 149, regfile64 150 (x2), regmerge 112, rest of the core 2,823 LUT + 338 ALU + 2,115 FF.
READING FOR THE BUDGET:
  - The skeleton alone already spends ~4,800 LUT4 + 426 ALU cells = ~5,200 equivalent LUT4, more than the 4,800 of the lean budget, and it still LACKS: semantic decoding of the 1,480 instructions
    (fields, addressing modes, sizes), CALL/RET/PUSH/POP/strings (state machines), I/O, length pre-decoding for 1 instruction/clock (+600 to 1,000 LUT4),
    interrupt/exception entry, connection to MMU/FPU/caches.  Estimate for the complete core: 6,200 to 8,200 LUT4 (typical ~7,800).
  - With the core at ~7,800, the lean budget rises from 17,660 to ~20,640 LUT4 (99.5 %): it does not close at 85 %. See the "Measured core" tab of spreadsheet rev10 for the levers (A+B+C+E lead to ~16,530 LUT4, 80 %).

== Flags of IN r,(C), IN F,(C), OUT (C),0 and interrupt in a repeated instruction ==
IN r,(C): S,Z,PV(parity),H=N=0, C kept (bit 73 'keepc' in the uop; extra uop OR r,r). tb_io: IO(C) OK.
IRQ: only accepted between uops (!seq); npc/epc hold the PC (in an LDIR it is the PC itself); IE disables on entry. tb_irq: IRQ IN LDIR OK
(interrupt with BC=3 in the middle of the repeat, handler returns by JR, final result equal to the one without interrupt).
Note: interrupt entry does not yet push the PC (epc is an internal register); Z80 IM0/1/2 semantics and RETI remain pending.

== Real interrupt entry ==
EI/DI (FB/F3), IM 0/1/2, RETI/RETN (restore IFF1 := IFF2), LD I,A, LD A,I (data only), level-triggered INT, IFF1/IFF2 cleared on acceptance.
IM0 and IM1: pseudo-instruction (opcode FF for the governor) pushes the PC and jumps to 0038h. IM2: vector read from [I:FF] (two 8-bit reads, so as not to cross a word).
Legacy IM (reset, im=3): jumps to CR41 without pushing (old behavior; tb_irq).
tb_irq2 (+im2): interrupt in the middle of LDIR (BC=3), handler LD A/OUT/EI/RETI, return to LDIR, correct final result: IM1 OK and IM2 OK.
Findings: (1) a 16-bit read at offset 7 of the 8-byte word crosses a word (known limitation of the skeleton) -> IM2 uses 2 8-bit reads;
(2) a partial write hb right after a write to the same register without slack overwrites the value (no WAW interlock) -> empty micro-operations in the IM2 chain.
Pending: flags of LD A,I (PV=IFF2); 1-instruction delay after EI; timing (governor uses that of RST: 11 T) vs real 13 T.

== Partial-write interlock (WAW / RAW with a partial producer) ==
Blocks issue while there is, in flight, a uop that PARTIALLY writes (8/16/32 bits without zero-extension, or high byte) a register that the new uop reads (A/B) or
merges (partial destination), and any in-flight producer for the same destination when the new uop is partial. Computed and registered (hz_q).
The empty slack uops of the chains (IN r,(C) with high byte, IM2, IN F,(C), LD A,I) were removed; all tests pass. Without the interlock, tb_io fails (proof).
Limitation: unused operand indices count (false positive only against a partial producer of the same register; it only costs time).
Fmax: seed 1 = 87.0, seed 3 = 90.0 MHz; LUT4 6136 (29%).

== Data interface with byte-enable and accesses that cross the 8-byte word ==
New port d_be[7:0] (core, cpu_gov, msx_sys): d_addr aligned to 8, d_wdata already in the lane (a 64-bit rotator), d_be marks the valid bytes.
An access that crosses the word (offset + size > 8) becomes two transactions (beat 0 in word A, beat 1 at A+8); the read reassembles the two beats (rotation + mask).
The testbenches stopped peeking at dut.addr_m (they use d_be). msx_sys: byte lane (mem_wdata/mem_addr) deduced from d_be.
IM2 went back to reading the vector with ONE 16-bit read at [I:FF]. tb_xing: PUSH/POP/CALL/RET with odd SP, transactions and byte-enables checked: WORD CROSSING OK.
Bugs found and fixed along the way:
 (1) a HOLD (slow access in M) froze the XR stage, but the synchronous output of the register file started following the next candidate -> wrong operand (CALL target = SP).
     Fix: under hold the register file read address is that of XR itself (a_xr/b_xr/d_xr).
 (2) seqc and ds counted clocks during the hold, shortening the producer-consumer distance (double INC SP lost an increment) -> now they only count without hold.
Cost: LUT4 ~7100 (34%); Fmax seed 1 = 83.1 MHz. Pending: extra time of an additional beat in the governor (R800/Z80) when the access crosses the word.

== Frequency recovery after the byte-enable ==
xing (crosses the word) and the next word address (addr8_m) are now computed in X3 and registered with the uop (off the hold path and off d_addr).
Fmax: seed 1 = 93.6 MHz, seed 3 = 89.4 MHz; LUT4 ~7017 (33%). Full regression OK.
"Second beat timing" pending item CLOSED: in the Z80/R800 modes the timing table already counts all bus cycles (including the two 1-byte accesses of a PUSH/CALL),
so the extra beat is an internal artifact of the 8-byte interface and must NOT add time; in native mode (no governor) the beat costs real cycles.
